Budget Tracker Security Review

A personal budget app that keeps every rupee of data encrypted on the person's own phone. We attacked the running app, fixed what broke, and attacked it again. Every finding is now fixed.

What we protect, and from whom

Transactions, budgets, goals, money given & taken and the profile live only on the device, encrypted with AES-256-GCM using a key stretched from the password (PBKDF2-SHA256, 600,000 rounds). There is no server and no cloud account.

Findings and fixes

Ordered by severity. Each one was reproduced against the running app before the fix and re-attacked after it.

4

A booby-trapped backup could freeze all encryption

HighFixed
What happenedA backup file could ask for 2 billion key-stretching rounds. It froze all encryption in the browser, even logging in, until the browser was restarted. Imported files had no size limit.
FixOnly 100,000 to 5,000,000 rounds and sane salt/IV sizes are accepted, checked before any work starts (refused in 7 ms). Files over 25 MB are refused.
OWASP A10OWASP A08T1499 Endpoint Denial of ServiceT1204.002 Malicious File
1

Private data stayed in closed forms after locking

MediumFixed
What happenedAmounts, notes, goal and person names and budget figures stayed in hidden form fields, readable by an extension or developer tools.
FixOn lock, every dialog and popup is closed, forms are reset and generated lists are emptied.
OWASP A04OWASP A06T1005 Data from Local SystemT1185 Browser Session Hijacking
2

The chart and a cache kept data in memory after locking

MediumFixed
What happenedThe doughnut chart and the note-suggestion cache held category names, notes and amounts after the app locked.
FixThe chart is destroyed and the cache cleared on lock.
OWASP A06T1005 Data from Local System
5

No Content Security Policy, and the app could be framed

MediumFixed
What happenedNothing in the browser would stop injected code if an XSS bug ever slipped in, and another site could show the app inside a frame (clickjacking).
FixA strict policy: script-src 'self', no inline scripts, no eval, object-src 'none'. The app hides itself when framed.
OWASP A02T1059.007 JavaScriptT1189 Drive-by Compromise
6

Reloading skipped the wrong-password wait

MediumFixed
What happenedThe wait after 5 wrong passwords lived only in memory, so a page reload reset it.
FixThe counter survives reloads, capped at 1 hour so nobody is locked out for days.
OWASP A07T1110.001 Password Guessing
7

Easy passwords were accepted

MediumFixed
What happened12345678 and password passed the 8-character rule. Anyone who copies the encrypted data can guess offline, so password strength is the real protection.
FixCommon passwords, runs (12345678, abcdefgh, qwertyui), one repeated character and the person's own name are refused, with a plain-words reason.
OWASP A07T1110.002 Password Cracking
3

A toast stayed visible on the lock screen

LowFixed
What happenedMessages such as "Added Rent ₹15,000" could still be read after locking.
FixCleared on lock.
OWASP A06T1005 Data from Local System

LowFixed

Accepted risks

Things no web app can fully remove, or that are deliberate.

  • Malware or a malicious browser extension can read the screen while the app is unlocked, or capture the password T1176 T1056.001. Install few, trusted extensions and keep the phone updated.
  • Offline guessing of a stolen copy T1110.002. 600,000 rounds and the password rules slow it down; a long passphrase is what really protects it.
  • "Forgot password?" wipes the data without the password T1485. Without the password the data can't be recovered anyway; backups and the 30-day reminder are the protection.
  • The first name shows on the login screen before unlocking. Low sensitivity, kept for friendliness.
  • CSV exports and older unencrypted backups are plain text. The app warns where they're made.
  • GitHub Pages can't send security headers. The CSP is set with a meta tag and framing is handled in a script instead.
  • JavaScript can't wipe strings from memory. Data is dropped on lock; the browser decides when the memory is reused.

Re-running the checks

Unit tests run with Node 18 or later, from the project folder. The browser attack sweep was run by hand in Chrome against a throwaway account; repeat it after any change that turns text into HTML.

node tests/security.test.mjs     # password rules, backup validation, prototype pollution
node tests/biometric.test.mjs    # fingerprint unlock with a simulated sensor
node tests/format.test.mjs       # exact money parsing
